结论摘要

SQLite 实测显示，最严重的路径主要由查询次数、无界响应或路由内外部 I/O 放大，而不是单条 SQL 慢。现有 comment 外键索引均被使用，无法修复 4N hydration；真正缺索引的热点集中在 tasks、project issue 聚合和列表排序。

P0

已验证 native issue detail 是最大组合放大器。 2,000 comments 下 GET /api/multiremi/issues/:id 为 8,034 SQL、p95 155.6 ms、响应 1.95 MB；路由把 tasks、全部 hydrated comments、activity 等一起组装（routers/issues.ts:649）。

P1

已验证·受控失败路径 repository GET 执行远端 Git I/O。 缺 default_branch 的种子仓库使 GET /api/workspaces/:id/repos 每次触发 git ls-remote；9 SQL 但 p95 243.0 ms（routers/workspaces.ts:297、helpers/repositories.ts:145/:267）。这不是数据库慢，且已填 default branch 的正常路径不会触发。

P1

已验证 task-runs 新 N+1。 500 tasks 中 125 queued，路由逐 task 调 getTaskQueueBlocker，共 129 SQL、p95 42.9 ms，并返回 916.4 KB（routers/issues.ts:744、tasks-repo.ts:145）。

P1

已验证 issue search 新 N+1。 200 issues 触发 200 次 comment snippet 查询，总计 202 SQL；每条子查询命中现有 (issue_id, created_at) 索引，问题仍是逐 issue 调用（issues-repo.ts:684/:733）。

P1

已验证 agents 两层 hydration。 native list 为 52 SQL；compat serializer 又逐 agent 调一次 listAgentSkills，compat list 达 150 SQL（agents-skills-repo.ts:676/:693、wire/agents.ts:14/:42）。

已验证 无界返回已成为独立成本。 GET /api/multiremi/tasks 仅 2 SQL，但 500 rows 已产生 634.0 KB 响应；issue lists 在 200 rows 时约 115–119 KB。

生产桥开销建模：沿用 MUL-172 已验证的 207–378 µs/SQL 阻塞地板，native issue detail / timeline / comments 仅桥往返均约 1.66–3.04 s，native issue list 42.0–76.7 ms，issue search 41.8–76.4 ms，task-runs 26.7–48.8 ms；均不含真实 Postgres 查询和网络时间。此段是建模推算，不是生产实测。
