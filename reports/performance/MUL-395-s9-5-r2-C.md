2026-10-05，本地真实 PostgreSQL 18.4 / UTF8、Bun 1.3.14。结论：本轮不改 C 产品代码。相同 `ec2599e4` 代码能重现 QA 的首次对齐耗时范围，额外耗时主要是同步桥等待；没有发现相对 S9-5 before 的代码倒退。首次对齐超过 10ms 的既有豁免不变，原报告 60.963ms 是一次本地采样，不能作为其他运行环境的上界。

## 桥等待证据与结论边界

工具保留每条语句的等待和字节，不记录 SQL 参数或凭证；六个流程末尾各执行 100 次无业务工作 `SELECT 1` 作为桥校准。

| 配对 | before / after 单条业务等待中位数 ms | before / after SELECT 1 等待中位数 ms |
| --- | --- | --- |
| 1 | 0.707 / 0.666 | 0.517 / 0.664 |
| 2 | 0.737 / 0.672 | 0.580 / 0.632 |
| 3 | 0.452 / 0.829 | 0.665 / 0.723 |

即使无业务查询的桥往返也有约 0.5–0.7ms 底噪，97 次串行往返会放大这类差异。`packages/server/src/store/db/postgres.ts` 的计时从发送后的 `Atomics.wait` 到 shared buffer 回复；它包含 worker 调度、数据库执行和回复等待，不能单凭这个指标继续区分具体是哪一项。这里将差异归因为**环境相关的同步桥等待波动**，不声称已经定位 QA 机器的 CPU/IO 原因，也不声称是生产数字。

每对 after 的查询数、字节及阻塞均低于其 before。现有限频方案确实减少往返，但首次对齐仍串行执行 97 条 SQL，不能保证任意环境都接近原报告的 61ms。这是原来已豁免的特殊分支成本，不通过修改业务语义压缩数字。

原始流程也保留稳态样本；本轮 version 阶段 after 的正式 timer 最大为 11.164 / 12.947 / 11.742ms，高于上一轮 QA 的同版本稳态最大 8.57 / 9.60ms。本轮任务只归因首次对齐，不能用这些数据宣称重新通过稳态 10ms 门槛；交付将这个环境差异一并交给负责人/QA。本轮未把 timer 校准值从实测阻塞中扣除。
