# MUL-395 S9-5 r2 B：未结束任务稳态回包

2026-10-05，本地 PostgreSQL 18.4 / UTF8、Bun 1.3.14。修复前为 QA 固定 head `ec2599e4ab4e6ce3b35b16fbfb1cefaaacb0a71e`。结论：两个指定档位 runtimes/models 的 **80/80 正式请求均 ≤50,000 bytes**；同口径修复前 80/80 超标。API 形状、逐字段值、顺序与 usage parser 口径保持一致。

## 修法与范围

PG 列表增加每 runtime 的未结束任务 token 缓存，使用现有 settled 缓存的 id/xmin 摘要机制。单条 SQL 在同一快照返回四项新计数、settled/open 两组摘要，只有与调用方已知摘要不同的那组才返回 `json_agg(usage)`。因此无写入/无失效的热缓存不再每次传回全部 open usage。

选择缓存合计而非 SQL JSON 数值解析，是为了继续调用原 `addTaskUsage` / `parseTaskUsageEntries`，原样保留 camelCase/snake_case 优先级、数值转换、缺字段、非法 JSON 的语义。SQLite 保留原扫描。超过 JS 安全整数范围时仍回退原始加法顺序；事务内既不读取缓存，也不发布缓存，避免同一 xmin 下两次写及回滚污染。

持久化 usage/status 更新、插入、删除、runtime 重绑都会改变对应摘要，下一次读立即生效，没有 TTL 或延迟可见窗口；SQL 计数每次重新计算。缓存只保存两个摘要及八个 token 数值，不保存任务 usage 数组。详情读取、过滤、owner/daemon 鉴权、模型/组响应和路由均未修改。

这是**无变化稳态**的回包修复：发生写入时，变化的 runtime 对应 usage 分组仍需重读；冷读、settled 失效和 execution-groups 重复 hydration 的既有豁免不变。SQL 仍扫描任务以验证摘要，DB 工作量仍随任务数增长，本轮不宣称解决这部分 CPU/阻塞增长。

## QA 同档位真实 PG 前后测量

工具 `tests/manual/bench-mul395-s9-5-open-cache.ts` 来自 QA 的 `bench-mul395-s9-5-qa-open-scale.ts`（评论 `cmt_08mcj02pfxht` 的 probe patch），沿用相同 fixture、计数器和计时方法。两份产品快照复制完全相同工具，SHA256 `581793ec3b60339a947605a67134d10b973da9b3f1623206a53b8934d44310e9`。

- 新仓库用例 `unchanged open usage has bounded bridge bytes and mutations remain immediately visible`：10 runtime / 200 running 的热读回包断言、逐 runtime 八字段原 parser 对拍、usage 更新、状态完成、重绑、同事务两次写、回滚、删除及清空 open 分组。
