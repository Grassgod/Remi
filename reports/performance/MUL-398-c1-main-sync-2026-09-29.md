## 桥与上下文

- 405 的迁移互斥锁 `pg_advisory_lock` / unlock、issue 编号事务锁 `pg_advisory_xact_lock`、父行 `UPDATE ... SET id=id`、BEGIN/COMMIT/ROLLBACK/SAVEPOINT、`SentinelPgStatement` 均通过同一个 `PgBridge.exec` / `PgBridge.request`。每个 SQL 回包都使用 `postgresReplyMaxBytes()`；启动迁移无请求上下文，命中独立 `<background>` 64 MiB 项，锁语句只返回极小的状态行。桥对每条 SQL 只调用一次 `recordDbQuery`；哨兵仅在执行前分类，不增加桥计数。拒绝依旧在 `TextDecoder` / `JSON.parse` 前。
- 405 给 `api_minute_summary` 和 `api_slow_request` 加 `pid`，没有改路由解析。`MULTIREMI_REQUEST_METRICS=0` 仍执行 `requestContext.run(state, next)`；开启/关闭指标均保留真实 HTTP method + Hono pattern，关闭时不采样、不输出请求指标。C-1 真 PG 用例覆盖关闭指标时的例外放行及非例外拒绝。
- `tests/setup/hermetic-env-policy.ts` 同时保留 C-1 的 8 MiB 测试默认值和 405 的默认开启锁序哨兵；`request-metrics.test.ts` 同时保留 C-1 上限断言与 405 的 `pid` 字段断言。没有放宽任一守卫。
