C模块 C · 项目绑机器(物化) 复用 local_directory

「代码在哪台机器的哪个目录」的唯一权威。不新建表——local_directory 资源({daemon_id, local_path})就是它,配套约束已存在(store.ts:7266 一机一目录)。

绑

两种绑定方式

  • 导入已有目录:代码已在机器上 → 选机器 → 目录扫描选路径(复用已做的 directory-scan)→ 写 local_directory
  • 自动 clone 新:项目挂 git URL → 选机器 → daemon 收到 provision 请求,clone 到标准路径 ~/.remi/projects/<slug> → 完成后自动写 local_directory

provision 请求复用现有"runtime 请求队列"机制(directory-scan / model-list / update 同款),不发明新通道。

?决策点与风险

D1 · key 在服务端怎么存? 内网单组织,DB 明文可接受吗,还是 server 环境变量注入/简单加密?
建议:先 DB 直存(和 master token 同级的信任域),重点保证 fleet 机器不落盘;后续要加密再说。
D2 · CLI 安装源:内网装 claude/codex 走公司 npm registry 是否通畅?(GitHub 需 proxy 是已知约束)
建议:P2 动手前先在一台机器手工验证两条安装命令;不通就走本服务器镜像分发(install-remi.sh 已有同款机制)。
D3 · 多用户还做不做? 与本方案正交:机器可见性(public/private)、成员权限那套冻结不动即可,两边不互相阻塞。
本方案在单人和多人模式下都成立;若日后继续多用户,只需给「项目绑机器」补权限校验。
D4 · 具体 env 键名:claude(ANTHROPIC_BASE_URL/ANTHROPIC_API_KEY 或 AUTH_TOKEN)与 codex(OPENAI_BASE_URL/OPENAI_API_KEY 或 config.toml)按当时 CLI 版本核对,凭证表用自由键值对,不写死。
  • 风险:自动 clone 的仓库鉴权(私有 repo 需要 git 凭证)——V1 可先只支持已配好 git 凭证的机器,或先只做"导入已有目录"
  • 风险:双 CLI 版本漂移——install 固定版本 + 复用 runtime-update 机制统一升级
  • 回滚容易:P4 之前所有改动都是加法;P4 有老判据兜底,关掉新判据即回到现状
